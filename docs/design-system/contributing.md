# 参与设计系统

设计系统是长期维护的公共约定。新增或修改前先确认现有规则是否已经覆盖，避免为单个需求增加永久特例。

## 变更流程

1. **确认问题**：说明是规则缺失、实现偏差，还是一次性的视觉调整。
2. **查找现有方案**：优先复用已有 token、组件或模式。
3. **提出方案**：涉及新 token、共享组件、断点或重要取舍时，按 [需求流程](../../features/README.md) 确认。
4. **实现**：同时更新代码与文档；文档只写当前规则。
5. **验证**：检查状态、响应式和已有页面。
6. **记录**：设计取舍、备选方案和验证结果写入 `features/work/`，不写进规范正文。

## 新增或修改 token

- 只有出现新的语义角色时才新增 token；一次性微调不升级为全局 token。
- 按 [Token 命名](../tokens/naming.md) 的语法命名。
- 更新所有引用，删除旧名称，不长期保留别名。
- 同一取值在代码中只定义一处、在文档中只列出一次；修改时同步对应文档。
- 修改颜色、字号、间距或圆角时，检查是否影响已有组件和页面。

## 新增或修改组件

- 先判断是否满足 [组件](../components/README.md) 的提取条件。
- 组件文档按模板编写，包含用途、结构、变体、状态、行为、内容、元素与状态、API 和相关模式。
- 组件变体保持正交，状态命名一致；不为单个页面增加特例属性。
- 仅视觉相似时使用 token 或局部 class，不添加转发组件。

## 文档规则

- 使用现在时和规范性表述，不写个人偏好、实现历史或方案辩解。
- 抽象规范不列具体组件名、页面名或项目组件清单；具体参考放在对应文档。
- 一个原则只保留一个维护位置，其他文件通过链接引用。
- 修改文档后检查相对链接、表格格式和与 CONTRIBUTING 的一致性。
