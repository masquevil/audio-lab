# 文档维护

## 先选落点

先读取当前文件和用户修改，判断反馈属于具体缺陷、实现偏好、通用原则还是流程问题。不是每次返修都要更新规范；已有规则足够时修正实现和执行，不追加同义规则。

| 文件 | 读者与用途 | 何时更新 |
| --- | --- | --- |
| [AGENTS.md](../../../AGENTS.md) | AI 入口、阅读顺序、skill 触发及执行边界 | 入口、执行约束或用户明确的项目偏好改变时 |
| [CONTRIBUTING.md](../../../CONTRIBUTING.md) | 开发者快速查阅的环境、目录与通用技术指导 | 存在可推广且尚未表达的开发原则时；用简短指导，不写纠错解释、逐项清单或业务案例 |
| `.cline/skills/*/SKILL.md` | AI 执行专项任务的触发条件、步骤和检查入口 | 专项执行流程改变或反复漏掉执行环节时；不复制开发规范与详细核查项 |
| [review checklist](../code-review/checklist.md) | reviewer 的判定方法、正反例和不通过信号 | 原则已有但缺少可操作的核查依据时；不作为开发阶段全文必读材料 |
| [features/README.md](../../../features/README.md) | 需求工作区结构、评审与确认流程 | 需求流转本身改变时，不记录某个需求的经过 |
| `features/pools/` | PM 原始需求 | PM 补充或确认修改原意时；研发评审补充优先进入 work |
| `features/work/` | 每个需求唯一的实施、评审、验证及验收记录 | 范围、方案、进展或真实验证结论变化时；保留结论，不粘贴对话、整段代码或调试日志 |
| [current-status](../../../features/current-status.md) | 活动项索引 | 阶段、下一步或阻塞变化时；PM 确认完成后移除条目，不复制历史记录 |
| [tests/README.md](../../../tests/README.md) | 单元测试组织与已确定的执行方式 | 测试工具或组织约定确定、变更时；不写临时验证脚本或虚构结果 |
| [README.md](../../../README.md) | 项目介绍与使用入口 | 用户可见能力、启动或使用方式改变时；不承担内部执行规范 |
| `docs/`、就近代码说明、`.ai/` | 分别承载必要的长期架构决策、局部实现约束、临时计划与调试材料 | 有真实维护需要才创建；临时材料不升级成长期规范 |

## 更新步骤

1. **核对现状**：检查 Git 差异、目标章节与关联引用，保留用户已做的简化。确认需要新增规则还是修正原有表述。
2. **最小修改**：优先改已有条目；一个原则有一个维护位置，其他文件通过链接引用。CONTRIBUTING 保持给人看的短指导；具体判断和非业务对照例放 checklist；执行步骤放 skill。
3. **保持边界**：具体缺陷修代码，结果写需求记录。推广检查相关调用链和同类实现，但不借机扩展功能或目录。重要职责或技术边界变化先按需求流程确认。
4. **同步迁移**：搬移内容时删除旧副本、修正引用。新建 skill 应有清晰的 name、description 和独立用途，并在 AGENTS 添加触发入口；没有独立用途就合并已有 skill。
5. **自审精简**：删除重复、教程化、辩解式内容。注释和留白服务阅读，不因“总结经验”堆积解释，也不为每次反馈增加全局规则。
6. **验证交付**：检查相对链接、章节引用、格式和规则冲突；报告实际改动及未覆盖项。仅文档变更不运行无关构建，不把自审称为独立 review 或人工验收。

本 skill 维护文档落点与更新流程；开发规范引用 CONTRIBUTING，需求状态与确认点引用 features/README，不在此复制其内容。
