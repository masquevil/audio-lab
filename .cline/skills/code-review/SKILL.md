# 技术代码审查

以其他研发或研发 leader 的技术审查视角，依据 [开发规范](../../../CONTRIBUTING.md#代码规范基线) 和 [checklist.md](checklist.md) 检查代码质量。不以了解产品需求为前提，不负责功能验收、场景测试或 QA。复用有效上下文，不重复全文读取规范。同一 AI 执行仍是自审，不宣称独立人员已审查。

## 执行步骤

进入本阶段再加载详细清单，围绕最终代码开展审查，不依赖实现过程中“已经考虑过”的解释。若有独立审查上下文，仅提供规范、清单、最终差异及必要关联代码，不要求重放产品讨论；同一上下文自审则明确其非独立性。

1. **确定代码范围**：查看 Git 状态和最终差异，包括新增文件；区分用户修改，明确比较基线，不覆盖改动。
2. **检查技术实现**：按清单审查目录与依赖、职责与抽象、状态所有权、副作用、类型契约、命名、代码组织、样式和文档。不只是格式检查，也应指出代码中可判断的技术缺陷。
3. **核对关联代码**：读取必要的调用方、配置与资源清理路径，判断接口使用、状态不变量和异步归属是否一致。依据代码作技术推理，不按产品验收项设计测试场景。
4. **报告 findings**：按影响排序给出位置、违反的规范或技术依据、影响和修改建议。不能由代码确定的行为标为需研发验证，不将推测写成已复现问题。静态工具结果可辅助审查，不作为技术质量结论。
5. **复审修复**：只要求 review 时不擅自改代码；开发交付中修复已确认问题后，重查差异与关联技术问题。运行验证交给研发验证步骤，不纳入 reviewer 的测试职责。

## 输出与交付

- 有问题时先给 findings，再说明审查范围和限制；无问题时写“本次代码范围内未发现技术审查问题”，不宣称功能正确或测试通过。
- 不执行浏览器场景、故障注入或需求验收来充当 review；需要这些证据时交由研发验证或 QA。
- 技术审查结论与测试结果在实施记录中分开记录，不另造重复报告。
- 同一 AI 的复审不是独立 review 或 QA，不模拟独立审查角色。
