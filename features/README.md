# 需求工作区

## 结构与唯一来源

- `pools/日期 标题.md`：PM 原始需求，长期保留；AI 修改产品意图前应确认，评审补充优先写实施记录。
- `work/同名需求.md`：每个进入开发的需求一份实施记录，含原文链接、范围/不做项、可验证验收标准、方案与任务、评审结论、验证证据和最终验收结果。小需求合并章节即可。
- `current-status.md`：只记录当前关注项的链接、阶段、下一步与阻塞；不是历史日志，也不复制实施记录。

完成后保留 pools/work 文件作为历史依据，从 current-status 移除条目，不必搬迁目录或维护另一套归档索引。原文已明确的内容以链接引用，避免重复维护。

## 轻量流程

1. 需求评审：研发阅读需求与现状，提出目标、范围/不做项、验收标准、待决事项及建议方案。有实质性选择时等待 PM 明确确认，再进入开发；宣布方案不等于已获确认。明确纠错和已批准范围内的普通实现细节由研发直接处理。
2. 技术评审（按风险）：新增依赖、自定义插件或长期基础设施，改变架构/部署/数据模型，或存在明显兼容性、性能、安全、维护风险及不同成本路线时，先给出备选方案、推荐理由、影响、风险和验证方式，再确认关键选择。简单需求可合并在需求评审中，不强制单独文档；记录相对规模/风险，不虚构准确工时。
3. 开发：更新当前阶段与下一步；加载 dev-cs-vue，按任务实现，保留用户已有修改。
4. 自检与验证：开发完成后加载 code-review 统一检查差异、命名和 import 等，实际运行检查及相关交互/异常测试，记录证据和限制。独立 review 可用时再安排，不模拟多人会议。
5. 待 PM 验收：提交清晰验收步骤。只有 PM 确认才标记完成并移出 current-status；小修回开发，范围变化回评审。

建议阶段：评审中 → 开发中 → 验证中 → 待验收 → 完成；阻塞时记录原因与所需决定。

开发中发现原方案不可行、必须扩展范围或产生新的重要维护负担时，回到评审确认；不自行扩张方案，也不把函数命名等普通实现细节推给 PM。PM 返修中，明确纠错回开发，范围或重要方案变化回评审。
