# 环境音模拟实施记录

原始需求：[环境音模拟](../pools/2026-10-31%20环境音模拟.md)

## 确认范围

需求允许研发自行决定本轮完成量。本次选择完整实现四项能力，全部声部由 Web Audio 实时合成，不引入音频文件；Moodist 等录音只用于提取参考规律，不进入产品：

- 新增 `/ambience` 页面及首页、主导航入口。
- 四种声部：风声、雨声、雷声、篝火。强度同时改变滤波、调制和电平（微风→飓风、细雨→暴雨等）。
- 每个声部可单独播放/停止；多声部可同时播放并各自调节。
- 混音录音：从混音总线录制，不请求麦克风权限；支持试听、下载、清除；最长 5 分钟。

不做：总音量、场景预设与保存、录音剪辑、后台持续播放策略。本记录的验证是 AI 自检，不是独立 QA。

听感返修经历：初版合成风声、雨声质量不足；改用真实采样后 PM 指出采样夹带目标外声音，且项目应以 Web Audio 合成为主。第二批反馈指出雨声像煎蛋、雷声闷且有鼓点、篝火风声压过木柴声。第三版撤掉采样，把参考录音保留在忽略目录，并改用程序化事件纹理（雨滴、木柴爆裂、雷声滚动）而不是稳定滤波噪声。第四批反馈指出雨声像打在异物上、雷声第一下过冲、篝火像八音盒、微风一直不停；第四版改为纯噪声脉冲、软起音和阵风门控。第五批反馈指出飓风被门控切出静音、雨声像电视雪花、雷声只有单道、低强度篝火仍太密；第五版改为多层风、低中频雨幕+稀疏雨滴、成组雷暴和低强度稀疏篝火。第六批反馈指出雨声仍不对、雷声开头过于统一、篝火整体像白噪声而缺少火苗扑腾，并要求多参考；第六版补到 7 个雨、7 个雷、5 个火参考，改成纯滚动为主的雷声变体、带簇雨滴和火苗扑腾层。最终 PM 明确要求参考音频只作为学习基准，产品实现必须是我们自己的模拟；雷声回到多事件合成，不使用 Moodist 文件播放。第七批反馈指出雷声/小雨仍不像，要求“把参考的结构抄过来再叠时间轴”，并用波形对照确认；本轮把 Moodist 雷声三段事件的 0.1 秒包络写成 profile 数据，轻雨去掉长周期 swell/river、改为平直底噪 + 近距滴落，并新增波形对照台逐次比较。第八批反馈指出雷声像单一长音、雨声应按多种音色比例变化；本轮把雷声拆成 1–3 个短单元错开触发，并试验五单元雨声比例。第九批反馈指出改完后暴雨反而变差、window 声消失，要求用回上一版最终音色；产品雨声先回滚到 light/heavy，五单元方案保留为离线实验。第十批反馈要求小雨直接按 Moodist 音色重做；轻雨先改为 52 段 1/6 倍频程平均谱，仍被指出是平铺噪声，于是再叠加约 8 次/秒近距滴落/飞溅；随后反馈滴落像篝火噼啪、没有水声，又加入很轻的 river 水流层并把滴落改成低中频水感冲击。第十一批反馈指出强风听不到啸叫；分析 Moodist howling-wind 后，把啸叫从常驻窄带噪声改成独立时间轴事件：900–1400 Hz、1.1–2.6 秒滑音。随后反馈啸叫像笛子、且弱风也有；去掉振荡器，改为相邻窄带噪声 + 宽带气流，并只在强度 ≥ 0.8 触发。再反馈啸叫时有一声较响的吹气、主啸叫不够明显；把宽带气流降到几乎为零，主共振 Q 提到 16–22、提高 gate 电平。第十二批反馈指出雷声仍有颤音、有气无力；先降重叠/固定速率。随后尝试 10ms 细包络，反而出现更快颤动、音量下降，于是回退到 0.1 秒包络，并提高单次雷声增益和淡入速度。第十三批反馈要求先忽略旧模拟，按 event1/event3 建一条尽量 100% 的轨道再谈压缩；本轮建立 52 段/20ms + 10ms 包络的高分辨率 event track，并让时间轴直接使用完整 event1/event3 轨道。随后反馈切片造成顿挫、惊雷起音毛糙；改为完整轨道 + 1.2s 长淡出，并加一级 5kHz 低通压掉高频毛刺。再反馈 event3 开头的闷雷仍毛糙；对 event3 前 2.4 秒单独做 100Hz 低切、1.2k/3k 低通和 0.85 增益，平滑接回全频轨道。随后仍觉得略毛糙，又对 event3 全段追加两级 8kHz 低通。音色确认后进入三阶段压缩：52 段/20ms 高分辨率基线 → 30 段并保留 attack 20ms/帧（149KB）→ 64 个谱状态码本 + 每帧电平（52KB）。VQ 版和 30 段压缩版都被试听报告毛糙/“炸麦”，高分辨率逐频段相加也被报告声音不对；最终产品改为低频滚雷重建，压缩数据只保留离线对照。第十四轮 PM 要求产品必须是 100% Web Audio、不得引入任何音频文件，并授权研发自行决定方案。本轮先做了归因：把旧产品纹理和 7 段真实雷声放在同一套指标下，频谱、峰值/有效值比、kurtosis、包络粗糙度和微峰密度几乎一致，说明前十三轮优化的都是“参考的外壳”——52 个频段各自独立噪声按帧增益相加，等价于保留幅度谱、随机化相位，恰好丢掉人耳识别雷声所依赖的瞬态与波前。因此放弃继续对齐频谱，改为按闪电通道几何重建**到达结构**：通道辐射元 → 声速延迟 → 距离衰减与低通 → 地面反射 → 地形回声，包络由到达叠加涌现，不再读取参考包络。

声部实现（最终版）：

- 风声：3 条独立白噪声链，每条经高通 110Hz、随强度变化的低通（300–1150Hz，Q 1.8–4.2）和独立慢速 LFO；强度决定启用 1/2/3 条，各层保留最低电平并互相补位。啸叫只在强度 ≥ 0.8 时触发：两条相邻窄带噪声（约 1000–1400Hz）+ 极轻宽带气流，与整体风量（`gustGain` 最高 2.4 倍）同步起伏；起始间隔 4–10 秒（阈值）收紧到 1.2–4.8 秒（满强度）。
- 雨声：light 用 Moodist Light Rain 的 **27 段 1/3 倍频程 × 20ms 包络模板**（31.5Hz–12.5kHz）在运行时重建，混入 0.5 倍共同成分把左右相关拉到约 0.45，末 1 秒等功率交叉淡化，循环 19.96 秒；heavy 是程序化雨幕（多层粉噪声 + 稀疏雨滴撞击，20 秒循环）。强度 0.3 以下只有轻雨，0.3–0.8 等功率交叉淡化，0.8 以上只有暴雨；两种纹理分别归一化到 -23 / -20dB RMS。
- 雷声：near / mid / far × roll / crack 共 5 个变体，每个用对应参考录音提取的 **24 段 × 20ms 能量包络**驱动运行时 STFT 重建（模板只存量化后的电平，不含音频）；强度决定落雷间隔（约 12 秒 → 1 秒）、距离抽样、起爆概率和同时重叠上限（1–3）。首次用到时渲染，其余变体按 1.5 秒间隔预热；停用时终止已排程音源。每次落雷的增益包络按实际 `playbackRate` 换算，淡出结束时音源同时停止，避免快放时尾音被硬切。
- 篝火：20 秒底纹（中频连续层 + 每秒约 30 次微爆，RMS -30dB）+ 运行时四种响爆（噗 15% / 木裂 13% / 啪 64% / 细响 8%，各带响度补偿）；密度 0.2→8 次/秒、间隔再乘 0.45–1.7 随机抖动、10% 概率成簇。滑块 0.2–0.8 映射为完整强度区间，`minLevelRatio` 0.92 让音量几乎不随强度变化。

立体声与空间：雨/火纹理左右声道独立生成（轻雨混入共同成分）；雷声每次落雷随机声像 ±0.65。所有声部经过 2.2 秒程序化卷积混响（湿声约 12%）进入混音总线和峰值保护压缩器（-6dB / 12:1）。纹理全部是运行时生成的 `AudioBuffer`，产品不包含外部采样文件。

参考分析（仅用于本地调参，不随项目发布）：除 Ambiently 的 rain、rain-heavy、wind、thunder、fireplace 外，另补 Mixkit 的 7 个雨、7 个雷、5 个火和 5 个风参考；裁成 30 秒片段后计算八度带能量、频谱重心、频谱平坦度、高频/中频比、包络变异系数、瞬态密度和静音窗口。参考文件保存在忽略目录 `.ai/reference-audio/`，供后续继续对比，不进入源码和构建产物；分析、临摹、验收与模板生成脚本在 `tools/sound/`，方法与实测基准在 `docs/sound-synthesis/`。

## 可验证验收标准

1. 未点击播放前没有声音；打开页面无控制台错误。
2. 四个声部可单独播放/停止，也可同时播放；调整任一强度时其他声部不受影响。
3. 风的强度从“微风”到“飓风”：层数由 1 增至 3，强度 ≥ 0.8 才出现啸叫，降到 0.8 以下啸叫消失。
4. 雨从“细雨”到“暴雨”：0.3 以下只有轻雨，0.8 以上只有暴雨，中间连续过渡、无突变或静音。
5. 雷在低强度稀疏、无规律，高强度出现更密集的落雷与起爆，且不会压过其他声部（整体不过载）。
6. 篝火在最低强度仍有声（不静音），强度提高后响爆密度明显增加，音量变化很小。
7. 录音只包含浏览器混音，不请求麦克风权限；停止后出现可试听、可下载的结果，“清除结果”能移除；“开始录音”最长 5 分钟后自动停止。
8. 播放中切换页面或刷新后声音停止、未完成的录音被丢弃。

## 历史轮次与实验记录

> 以下内容记录历轮返修与测量，其中“当时/上一版”和已删除的实验实现（到达事件模型、五单元雨声、试听页、开源参考区块）不代表当前代码；当前实现以本文件“方案”“声部实现（最终版）”为准。

此前只有“频谱对齐”，没有把层数、事件率和空档变成可验证指标，导致参数能对上但听感跑偏。第六版按以下流程执行：

1. **多参考测量**：雨/雷/火各取 5–7 个真实录音样本，计算音色和结构特征，不靠单个样本猜。
2. **规则化**：把听感拆成层数、事件率、重叠/空档、频谱平衡、调制五类；先写规则，再写合成参数。
3. **合成**：按规则选择多声源叠加、事件调度或噪声纹理，不用一个总增益解决所有问题。
4. **离线验收**：生成纹理后用 `analyze-wav.mjs` 对比参考分布；用 `OfflineAudioContext` 验证风/雷的层数和动态是否满足规则。
5. **人工听感**：离线指标通过只代表结构不跑偏，最终由 PM 在真实设备试听；不通过则回到第 2 步补特征。

火参考包含风声混入、过安静或短促音效的样本，只用来看变化范围；雷参考多数没有强起爆，验证了“起爆不是必备”。

结构规则与实测：

- 风：主风层活动层数按强度为 1/2/3；三条 LFO 使用不同频率和相位。排除启动淡入后，飓风 100 ms 包络最低值比中位数低 3.5 dB、CV 0.16，无静音窗口；微风 CV 0.31，起伏更明显。参考 howling-wind 的窄带峰值约 950–1240 Hz、事件持续约 1.5–3 秒；啸叫只在强度 ≥ 0.8 出现，中心 900–1400 Hz、主共振 Q 16–22、宽带气流几乎关闭，1.1–2.6 秒，3–5.5 秒一次，弱/中风完全不触发。
- 雷：到达事件模型。到达率由辐射元间距（3m，渲染取一半）决定，约 50–60 次/秒；每个到达的带宽随距离变窄（截止 = `90 + 9000·e^(-距离/吸收尺度)`，近雷约 6.6kHz、远雷约 2.2kHz，再经两级一阶低通），衰减时间随距离从 30ms 增到 480ms（生成核上限 280ms）。近雷 3 次回击、中雷 2 次、远雷 1 次；远雷用更小的抬升比例模拟云间水平放电。实测：近雷 peak/RMS 22.1 dB、kurtosis 17.6、10ms 包络粗糙度 0.314、微峰 7.2 次/秒、频段分布与参考 event1 相差 0.5–3 dB；中雷 22.5 dB / 18.9 / 0.326 / 8.2；远雷 19.2 dB / 11.2 / 0.300 / 8.7（远雷更平、更连续，符合距离越远越没有起爆的听感）。
- 雨：产品暂时使用上一版 light/heavy 交叉淡化（低强度轻雨，0.35–0.8 进入暴雨），保住已经认可的暴雨音色。五单元实验（heavyWash/window/carRoof/lightWash/river）仍可用离线脚本 `mix-rain-units.py` 试听比例，但**尚未接入产品**。

- 火：12 秒循环；低强度约 0.17 次 crackle/秒、0.08 次扑腾/秒（约每 12 秒 2 次爆裂、1 次扑腾），高强度约 10 次 crackle/秒、1.4 次扑腾/秒。小火用平方交叉淡化，几乎关闭旺火纹理；低强度不再叠加 12 kHz 高频床，避免底噪自带细碎噼啪。

混音与录音：各声部 → 主增益 0.8 → 压缩器 → 扬声器；主增益另送约 12% 到卷积混响，再汇入压缩器。压缩器只做峰值保护（阈值 -6 dB、knee 6、比例 12:1、启动 5ms、释放 200ms），避免把雷声瞬态压平。录音时从压缩器输出接入 `MediaStreamAudioDestinationNode`，由 `MediaRecorder` 按浏览器支持顺序选择 WebM/Opus、WebM、Ogg 或 MP4，停止后生成 Blob URL。播放与录音共用同一 AudioContext；无活动声部且不在录音时淡出并关闭，页面卸载时立即关闭。

## 雷声与纹理方案：临摹 → 拆解 → 生成（记录）

> 本节按时间顺序记录方案形成与返修。最终实现见上方「方案」「声部实现（最终版）」；下文提到的 `.ai/*.py`、`blockSize`、`splitSeconds`、A/B 分段参数、`addBed` 烘焙 LFO、`rainLightSpectrum` / `thunderProfiles` 等已被后续实现替换或删除，只作为历史依据保留。

PM 明确要求不使用任何音频文件，并指定顺序：先证明能临摹真实雷声，再从临摹数据里拆出 A（起爆）和 B（持续），最后生成新样本。

**1. 客观判据**：用 AudioSet 训练的 AST（人类标注类别）作为第三方判据，脚本 `.ai/perceptual-check.py`；分布检验用 `.ai/verify-distribution.py`，特征包络检验用 `.ai/verify-envelope.py`。10 段真实雷声中 P(Thunder) 为 0.001–0.895（`thunder-1279/1280` 两段真实录音只有 0.001/0.014），所以单点概率只能当分布证据，不能当唯一验收。

**2. 临摹能力（已验证）**：`.ai/imitate.py` 把一段录音分解成 48 个 1/6 倍频程 × 10ms 的时变包络，再用纯合成重建。结果：平滑包络相关 0.967–0.969，整体包络误差 2.8–3.3 dB；P(Thunder) 与原声接近（event-1 0.26→0.31，event-3 0.73→0.59，1299 0.87→0.86）。PM 试听 event-1 / event-3 的临摹结果，反馈“还不错”。这证明合成引擎与包络表示是够用的，此前的失败来自我自造的时频结构。

**3. A / B 拆解（10 段真实录音，`.ai/decompose.py`）**：A 段起音中位 500ms（40–2910ms）、持续中位 0.61s、频谱以 100–400Hz 为主（-5.6 ~ -5.8dB），3.2–8kHz 低到 -36dB；B 段与 A 段频谱几乎相同，差别在包络——每 45ms 一次起伏（约 22 次/秒）、整体以 -1 ~ -4dB/s 衰减、B 段峰值可达全局峰值的 0.85。另测：各频段与总包络的相关为 0.59–0.93（不是 1.0），高频衰减更快（2.8k 段 -5.5dB/s，低频 -3.2dB/s），调制能量 24.6% 在 0.1–0.2Hz、约 26% 在 12.8–51.2Hz（`.ai/band-dynamics.py`、`.ai/modulation.py`）。

**4. 隔离实验**：真实时间包络 + 我的频谱配比 → P(Thunder) 0.41；我的时间包络 + 真实频谱配比 → 0.10；真实全部 → 0.59。结论：**决定判定的是时间包络，频谱配比是次要因素**。

**6. 最终采用的方案：实测包络模板 + 运行时合成**。从零构造包络试了六种参数化方式（几何到达、统计包络、roll 脉冲、连续随机过程、单元重组、调制谱匹配），最高只到 0.34 且对随机种子敏感；roll 序列还会被判成鼓/音乐。可靠的做法是：把真实录音的时频结构压成**紧凑模板**（24 个 1/3 倍频程 × 20ms 的能量包络，量化到 1dB 的 uint8，base64 存放），运行时用分块 STFT 按每帧能量铺随机相位再逆变换，得到全新的波形。模板只是能量数据，不能播放；波形全部由运行时噪声生成。块长最终为 1024 点、256 跳（4 倍重叠；过程中曾用 2048 点，瞬态更模糊）。

- 提取脚本现为 `tools/sound/build-envelope-data.py`，生成 `src/views/ambience/models/thunderEnvelopes.ts`（三套模板共 53KB 源码）；通用重建在 `envelopeTexture.ts`，`thunderEnvelope.ts` 只保留五个预设。
- 合成器入口：`createThunderEnvelopeTexture(rate, { preset, seed, timeScale, tiltDbPerOctave, gainDb })`，单条渲染 53–125ms。
- 生成新实例靠时间伸缩（0.8–1.1×）、频谱倾斜（±2dB/oct）、整体增益和随机种子；五个变体映射到三套模板。
- 判定结果：near 0.31、mid 0.49、far 0.61（对应原声 0.26 / 0.73 / 0.46），三段均为 Thunder Top-1；PM 试听上一轮同方案的三段候选，反馈“还不错”。
- PM 复听后的两处修正：① far 模板（thunder-1300，不是 1299）自带雨声底噪，PM 听出“底噪里有一点雨声”，只对 far 模板在 800Hz 以上按 20 分位减去固定底噪（避开 30–800Hz 的雷体），Rain 概率 0.10→0.06；② mid 的起爆“稍微有点失真”，原因是 STFT 块长 2048 点（42.7ms）抹开了瞬态，默认块长降到 1024（21ms）：mid 的 P(Thunder) 0.31→0.46、near 0.16→0.29、far 0.42→0.55。
- near/mid 的模板数据在修正中逐字节未改（只改 far 模板与块长）；`blockSize` 选项已在复审中随未接线代码删除，仅作历史说明。
- 修正后五个变体：nearRoll 0.29、nearCrack 0.17、midRoll 0.46、midCrack 0.36、farRoll 0.55；Rain 0.03–0.07；浏览器冷渲染 45–116ms，控制台 0 error。

- 模板扩充：追加两个无雨声候选模板（1279 深沉、1280 近距长雷），离线渲染为 `cand-deep.wav` / `cand-close.wav`；判定值只有 0.01 / 0.05，与它们原声（0.001 / 0.014）一致，说明分类器对这类极低频闷雷不敏感，是否采用需 PM 试听后决定，暂不进入产品数据。
- PM 反馈“强度只体现在音量上，应该影响打雷频次”。排程改为 `0.8 + 11.2·(1-强度)^1.6 + 抖动`（最低约 12 秒一次、最高约 1 秒一次），重叠上限从 2 提到 3（≥0.85 时）。浏览器内统计 `AudioBufferSourceNode.start`：强度 0.1 时 25 秒内 1 次、0.95 时 9 次且始终有雷声在响。
- 多声部响度统一：新增 `normalizeLoudness`（按 RMS 统一到 -20dB 再限峰），雨/火/雷的纹理先统一基准，再按实测重设 `maxGain`。端到端实测（默认强度、压限器之后的有声段 RMS）：风 -29.3dB、雨 -29.0dB、篝火 -31.0dB、雷 -24~-25dB（雷是间歇事件，峰值帧约 -14dB）。改动前为：风 -26.6、雨 -39.4、篝火 -30.9、雷 -30.2，即“篝火与雷几乎一样响、雨低 9dB”。
- 清理：删除已被替换的雷声实现（`thunderField.ts` 及其 573 行几何合成、`thunderProfiles.ts`、`thunderSpectralData.ts`、`thunderTrackData.ts`）、五单元雨声实验（`createRainUnitTexture`/`getRainTexture`）、页面“开源雨声参考”区块与组件、`features/pools/ambience-waveform.html`；进阶来源改记到 `docs/sound-synthesis/references.md`。`.ai` 只保留参考音频与 9 个候选 WAV，脚本与生成产物清空。构建产物 ambience chunk 82.6→80.8kB。

- 取舍说明：这套做法会随代码携带由分析得到的**能量包络表**（与已删除的旧数据文件 `rainLightSpectrum`、`thunderProfiles` 类似），不含任何音频采样，运行时是 100% Web Audio 合成。
- 第三轮 PM 反馈的三处修正：
  - **轻雨仍偏响**：`normalizeLoudness` 末尾调用的峰值归一化是**双向**的（峰值低于 0.98 时会放大回去），把前面的 RMS 目标整个抵消，所有纹理实际都被拉到峰值 0.98。改成只在超限时向下压之后，轻雨纹理落到 -23dB、暴雨 -20dB，轻雨端到端从 -26.1dB 降到 -31.6dB。
  - **最大雨里还有小雨音色**：交叉淡化区间从 0.35–0.8 前移到 0.3–0.8，并且 ≥0.8 直接返回纯暴雨，不再靠 `setTargetAtTime` 缓慢衰减残留。
  - **小火是"噗-噼-啪"固定循环**：根因是 12 秒纹理里只放了两三次爆裂、一次扑腾，转一圈就重复同一时序。改为纹理只保留连续底噪（同时去掉 `addBed` 烘焙的正弦 LFO，它让底噪起伏也跟着每 12 秒重复），木柴爆裂与火苗扑腾改为运行时随机排程：爆裂 0.18–10 次/秒、扑腾 0.06–1 次/秒，间隔乘 0.45–1.7 随机系数，8% 概率生成 2–4 声的短簇。实测强度 0.4 时 20 秒内 12 个事件、间隔 1.37/2.58/2.1/0.96/2.35/1.74/0.59/2.44/1.98/0.18/1.81 秒，无固定周期。
  - **强风呼啸**电平从 4.8–5.6 降到 3.6–4.4（-2.6dB），时长 1.4–3.0→0.8–4.0 秒，间隔 4.5–7→3.5–11 秒。实测 26 秒内 4 次，间隔 7.96/4.37/7.9 秒，门控电平 3.87–4.28。
  - 因归一化修正，篝火的 `maxGain` 从 1.45 调到 0.46 才回到原来的实测电平（-31.3dB）；雷的纹理结果不变（本来就是限峰后 -21.5dB），`maxGain` 保持 1.05。
- 第四轮 PM 反馈的三处修正：
  - **强风极短呼啸太多**：时长从 0.8–4.0 秒的均匀分布改成 `1.8 + 2.4·√U`（1.8–4.2 秒、均值 3.4 秒），短于 2 秒的只剩 0.7%。
  - **小雨音色不像 Moodist Light Rain**：根因是 20ms 帧的包络模板把 3–8ms 的雨滴撞击抹成了能量块，重建结果只是“雨雾”。改为**模板底纹 + 程序化雨滴**：先把模板归一化到 -23dB（否则补的事件会被整体归一化吞掉），底纹再压 6dB，按重尾分布补 80 次/秒雨滴（1.5–8ms、2–12kHz），并对 300Hz 以下做 +4dB 搁架补偿。实测命中 32.5 次/秒（参考 33.0）、>+3dB 命中 11.8 次/秒（参考 10.5）、>+6dB 2.4 次/秒（参考 1.9）、命中电平 p50/p90/p99 = 2.5/5.5/8.6dB（参考 2.4/5.0/9.7），频段占比 -25.9/-7.5/-1.0（参考 -24.9/-7.7/-1.4）。暴雨也补了同样的短促点击：>+3dB 命中从 0.5 提升到 12.7 次/秒（参考 13.7）。
  - **篝火整体重做**：实测参考 Campfire 的能量几乎全在 2–10kHz 的爆裂上（低频占比仅 -11.4dB、高频 crest 22.7dB），而我们旧版是 brown/pink 噪声层主导（低频占比 -0.8dB、高频 crest 1.5dB）——这正是“强火底纹太高、像噪声不像柴火”的原因。

    - 小火爆裂按反馈略微提高音量、加快频率（默认强度从 0.18 次/秒 → 0.43 次/秒）。
    - 重新标定 `maxGain` 0.46→1.7：默认强度实测 -31~-34dB（随底纹起伏浮动），满强度 -25.7dB、峰值 0.96。
- 第五轮 PM 反馈的三处修正：
  - **强风呼啸**：电平再降约 1.5dB（3.6–4.4 → 3.0–3.7），同时靠尖锐度补偿——共振中心从 820–1160Hz 提到 1000–1370Hz、Q 16–22 → 22–32、二次谐波 Q 10–14 → 14–20 且增益 0.12–0.2 → 0.2–0.32。
  - **雨声回退**：上一轮给轻雨/暴雨补的“程序化雨滴”被判定比模板版更不像，已全部移除。轻雨回到“Moodist Light Rain 包络模板 + STFT 重建”的原样（命中 28.2/秒、>+3dB 3.6/秒），暴雨回到原程序化纹理（命中 22.6/秒）。结论：参考里的“雨点感”与底纹同源，按指标补离散点击反而更假；已记入 method 的负结果。
  - **篝火底纹**：用 1ms 帧拆解发现真正差距在“事件电平”——参考的爆裂只比底纹中位高 **5dB**，说明底纹本身是连续有声的柴火；而我们上一版是“近乎静音 + 高出 21dB 的稀疏爆裂”，所以听起来像零星响指。改为：高频连续底（pink 7k/10k/2k/600 + 轻 brown）+ 180 次/秒微爆裂（1.5–6ms、电平起伏小）+ 12 次/秒木裂 + 0.6 次/秒低频噗。实测事件电平 p50 = 6.6dB（参考 5.0）、超阈值占比 18.7%（参考 24.4%）、频段占比 -12.9/-4.9/-3.0dB（参考 -11.4/-5.0/-2.6），各倍频程除 1k 偏高 2.8dB 外均在 2dB 内。播放电平：默认强度 -32.4dB、满强度 -23.2dB（峰值 0.91）。

## PM 验收步骤

1. `pnpm dev` 打开首页，点击“环境音模拟”，确认导航和返回正常；先调低设备音量。
2. 播放风声，把强度推到“飓风”（≥0.8）：确认 3 层风持续有厚度，且每隔几秒出现一次约 1–1.4kHz 的短啸叫；再降到“疾风/强风”以下，确认啸叫完全消失，只剩主风层。
3. 播放雨声并从“细雨”推到“暴雨”：确认轻雨有连续雨幕和空气感、不像篝火噼啪；推到 0.8 以上应变为更厚、更低沉的暴雨，中间过渡不跳变。
4. 播放雷声，从“远雷”推到“惊雷”：低强度应是稀疏、时长约 6–7 秒的低频滚动；高强度应更密集、偶尔出现更亮的起爆，并且两簇可能重叠。重点听三件事：有没有“整段是一层噪声被调音量”的机械感、起爆是否过冲或像鼓点、滚雷的强弱起伏是否自然、尾音是否被突然切断。建议戴耳机（笔记本外放听不到 40–100Hz，任何雷声都会显得薄）。
5. 播放篝火：低强度“余烬”应是少量噼啪 + 几乎听不到的连续底纹，不是稳定白噪音；高强度“烈焰”才明显密集、明亮；木柴声不应被风声压住。
6. 同时播放两到四种声音，分别调节强度，确认互不影响且可以混合，整体不过载。
7. 点击“开始录音”，保持一段时间后停止；试听、下载结果，确认内容为当前混音且未请求麦克风权限；再试用“清除结果”。
8. 播放中切换页面或刷新，确认声音停止；在手机或 Safari 上复核布局与录音兼容性。确认后再将需求标记完成。

## 音频总线拆分（技术返修，不改变声音）

PM 在 review 中判定：声源与录音都依赖“页面唯一的一条音频链路”，但这套所有权原先藏在 `useAmbience` 里，`useRecorder(acquireBus)` 实际是从某个具体特性借总线，换页复用必须重写一套。本轮按“页面级总线 + 声源注册 + 消费租约”重做：

- `types/audioBus.ts`：`AudioBusPipes`（`context` / `input` / `output`）、`AudioBusLease`（`onLost` / `release`）、`AudioBusHost`、`AudioBusController`。
- `models/audioBus.ts`：页面级实例（上下文、主增益 0.8、峰值压缩器）、租约表、`acquire()` / `dispose()`。最后一个租约归还后淡出 120ms、等待 160ms 再关闭，沿用拆分前的停止时序。
- `hooks/useAudioBus.ts`：能力探测、总线错误与 `onUnmounted → dispose`；页面内只调用一次。
- `models/ambienceMix.ts`（原 `ambienceSession`）：只建声部图与环境音混响并接到总线 `input`，不再创建或关闭上下文；正常停止时延迟 160ms 断开节点，避免最后一段衰减被硬切。
- `hooks/useAmbience(host)`：首个声部开启时借总线并建混音，最后一个声部关闭时归还；`onLost` 时停止并复位。返回 5 个字段（`intensities`、`activeLayers`、`error`、`toggleLayer`、`setIntensity`）。
- `hooks/useRecorder(host, options)`：只依赖 `acquire`，实现与拆分前一致。
- 视图组合三个 hook；声部、总线、录音三处错误分别提示。

保留的行为：主增益与压缩器参数不变；录音仍抽压缩器之后的输出；无声部时停止录音仍生成静音文件（待 PM 决定）；启动或恢复失败仍回到停止状态并提示。总线实例仍按“最后一个借用方归还即释放”处理，不常驻。

验证：`pnpm check` 通过（ESLint、Prettier、vue-tsc、构建；ambience chunk 118.64 kB，gzip 61.59 kB）。Chromium 本地 dev 实测：

- 双声部播放、逐个关闭、全部关闭后重新播放：状态与按钮一致，重新播放建立新实例。
- 播放中开始录音 → 关闭唯一声部：录音继续；停止后生成 32802 字节结果、文件名 `ambience-mix-20261103-000511.webm`，随后总线释放。
- 录音中通过应用内导航离页：无控制台错误与未处理拒绝。
- 注入 `AudioContext.resume` 失败：声部与录音分别提示，状态回到“就绪”，无未处理拒绝。
- 注入 `MediaRecorder` 构造失败（有声部）：仅录音提示，声部继续播放；停止后再播放正常。
- 放慢 `resume` 至 300ms 并在此窗口内反复开关同一声部：只创建 1 个上下文；全部关闭后再开启创建第 2 个。

未覆盖：`onLost` 在真实浏览器中没有自然可达的界面路径（需要“会话销毁时仍有借用方”），只经代码审查与单借用方卸载路径覆盖；停止尾音沿用原淡出时序，但未做真实听感复听；Safari/iOS 与移动设备；录音内容人工试听；独立 QA。

## 待排查 / 待试验

- **首播卡顿（本轮已处理）**：页面空闲时按 48kHz 预生成雨/火三个纹理（`textureWarmupTasks` + `requestIdleCallback`，采样率与实际不符时首次点击仍按真实采样率重新生成）。实测三批分别 210 / 358 / 181 ms，命中缓存后取用 0 ms；预生成期间若立刻点击，仍可能遇到一次 0.2–0.36 秒卡顿。分段渲染、Worker、实时节点均未采用（0.5 秒延迟用户判定可接受）。
- **纹理压缩（结论：不作为重点）**：参数数据本身很小（轻雨 28KB，解码 + 量化还原约 1ms），而渲染 204ms、纹理缓冲 7.3–7.7MB/条；压缩参数只减 bundle，对首播与内存帮助有限。暴雨/篝火本来就是程序化生成（0 字节数据），没有素材可压。
- **内存双份（暂不处理）**：产品优先保证使用体验，不以省内存为目标；当前纹理 + `AudioBuffer` 约 86MB。
